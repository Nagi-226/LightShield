# ADR-v052：LightShield "离线"语义选型 — 无需持续联网授权 vs 纯离线

> **状态**：✅ Accepted
> **日期**：2026-07-09
> **决策者**：Claude Code（架构 + 安全终审）
> **关联**：`adr-v052-r2-multi-target-redesign.md`（R2 多目标边界）、`.guardrails/PROGRESS.md`（v0.0.52 ADR 冲刺）
> **类型**：产品身份定义 → 范围漂移阀值「架构模式改变→🟠 暂停+ADR」强制立项

---

## 1. 背景（Context）

### 1.1 问题：README 说"全程离线"，代码已经联网

LightShield 的 README 宣称：

> 它不依赖商业安全平台或云端服务，只需一条命令即可对自有资产完成……全程离线运行。

但代码中实际存在 **4 处出站网络行为**：

| # | 模块 | 行为 | 触发方式 | 目标 |
|:--:|------|------|------|------|
| 1 | `rules/engine.py:202` | `import_rules_from_url()` — HTTP GET 远程规则 JSON | CLI `--rules-url` | 用户指定的 URL |
| 2 | `scanners/component_checker.py:1950` | `fetch_latest_cves()` — HTTP GET NVD API 2.0 | CLI `--cve-update`（手动） | `services.nvd.nist.gov` |
| 3 | `utils/notifier.py:60` | `send_bark_notification()` — HTTPS 推送扫描结果到手机 | CLI `--bark-key` / 环境变量 `LS_BARK_KEY` | `api.day.app` |
| 4 | `scanners/web_vuln_scanner.py` 等 | `requests.get(target)` — 向扫描目标发起 HTTP 检测 | 扫描流程自动 | **扫描目标本身**（非外部服务） |

> **注**：#4 是扫描行为（探测目标资产），不是"回连外部服务"。它不属于本次"离线"定义需要裁决的对象——本 ADR 只关心 LightShield **向外发出的、不以扫描目标为目的的网络请求**。

此外，`PROGRESS.md:476` 已记录了离线定义对下游的阻塞效应：

> v0.0.55 CVE 扩充：NVD 同步行为**取决于 v0.0.52 ADR-B**：纯离线 → `fetch_latest_cves()` 仅手动触发；非持续授权 → 可选 `--auto-sync-cve`

### 1.2 为什么现在必须定

1. **产品身份模糊**：README 说"全程离线"，但 `--rules-url` 和 `--bark-key` 都要求出站网络。用户读到 README 后发现有联网功能，会产生信任落差。
2. **阻塞两个后续 ADR + 一个版本**：
   - `adr-v052-r2-multi-target-redesign.md` — 资产清单来源（本地文件 vs 远程 CMDB）取决于离线定义
   - v0.0.55 CVE 扩充 — `fetch_latest_cves()` 的触发策略（手动 vs 自动）
   - v0.0.54 Nuclei 模板同步 — 是否允许从外部源拉取模板
3. **合规红线 R1 间接相关**：如果"离线"意味着"零出站"，那么 Bark 通知也属于违规（向第三方服务发送扫描目标信息）。

### 1.3 当前实际行为（事实基线）

```
默认行为（零 flag）： 零出站请求                                 ✅ 符合"纯离线"
--rules-url：        用户主动指定 URL → 出站 HTTP GET            ⚠️ 打破"全程离线"
--bark-key：         用户主动配置 → 扫描完成后出站 HTTPS          ⚠️ 打破"全程离线"
--cve-update：       用户主动触发 → 出站 HTTPS 到 NVD            ⚠️ 打破"全程离线"
```

**事实上已经是 opt-in 模型**——所有出站功能都需要用户显式传 flag。README 的"全程离线"描述的是默认行为，但没有解释 opt-in 联网功能的存在和边界。

---

## 2. 决策（Decision）

**LightShield 采用"无需持续联网授权"（No Continuous Network Authorization）作为产品离线定义。核心扫描功能零网络依赖；所有出站网络功能独立 opt-in、失败静默、不阻塞核心流程。**

### 2.1 定义

| 术语 | 含义 |
|------|------|
| **核心扫描流程** | `scan` / `harden` / `harden --closed-loop` 的资产探测+漏洞检测+加固生成+闭环执行路径。**永远不发出以非扫描目标为目的的出站请求。** 注：DNS 解析（将域名解析为 IP 地址）是扫描目标可达性的前置步骤，视为核心流程的一部分——此出站请求以扫描目标为目的，不违反铁律 1。 |
| **补充网络功能** | Bark 通知、远程规则导入、CVE 更新、未来可能的模板同步。**必须用户显式 opt-in，独立开关，互不绑定。** |
| **离线运行** | LightShield 的默认形态——不传任何联网 flag 时，零出站请求。无需互联网连接即可完成全量核心功能。 |

### 2.2 三条铁律（不可违反）

```
铁律 1：默认零出站
  → 不传任何网络相关 flag 时，LightShield 不得发起任何不以扫描目标为目的的出站请求。
  → 预热检查/更新检查/遥测/匿名统计/版本检测 —— 一律不做。

铁律 2：独立 opt-in
  → 每个网络功能一个独立 flag/配置项，互不绑定。
  → 不允许"启用通知即自动同步 CVE"或"导入远程规则即发送遥测"之类的捆绑。

铁律 3：失败静默，不阻塞核心
  → 网络功能的失败不得影响扫描/加固/闭环结果。
  → 现有行为保持：Bark 失败 → NotifyResult(success=False)，不抛异常；
    rules-url 超时 → print 警告，继续使用内置规则。
```

### 2.3 拒绝"纯离线"（方案 B）

**纯离线定义**：LightShield 永远不发起任何出站网络请求（包括 opt-in）。所有外部数据（规则/CVE/模板）必须通过文件系统手动导入。

| 维度 | 纯离线（方案 B） | 无需持续授权（本决策） |
|------|:--:|:--:|
| 默认行为 | 零出站 ✅ | 零出站 ✅ |
| 用户选择权 | 无——永远不能联网 | 有——用户可以 opt-in |
| `--rules-url` | 删除或降级为 `--rules-file` | 保留，显式 flag opt-in |
| `--bark-key` | 删除 | 保留，显式 flag opt-in |
| CVE 更新 | 仅手动复制粘贴知识库条目 | `--cve-update` 手动触发 |
| README 描述 | "全程离线运行" | "核心功能离线运行，可选联网增强" |

**否决纯离线的核心理由**：

1. **过度限制用户自主权**：Bark 通知是用户安装 App、获取 Key、主动传 `--bark-key` 的明确 opt-in 行为——阻止它不会提升安全性，只会降低可用性。
2. **CVE 知识库更新是刚需**：内置 105 条 CVE 静态数据必然过时。纯离线意味着用户需要手动从 NVD 网站复制 CVE 条目再粘贴进代码——这比 `--cve-update` 更容易引入人为错误。安全工具提供过时的漏洞数据，本身就是一种安全风险。
3. **"纯离线"不可验证**：用户无法审计一个 Python 进程是否真的零出站（需要 Wireshark/tcpdump 级别的网络监控），而 opt-in 模型是**可审计的**——用户知道自己传了哪个 flag，也就知道哪些功能会联网。
4. **与现有代码一致**：当前代码事实上已经是 opt-in 模型。纯离线需要删除 `import_rules_from_url`、Bark notifier、`fetch_latest_cves`——这是破坏性变更，受益有限。

### 2.4 现有功能的分类归属

| 功能 | 分类 | 联网目标 | opt-in 方式 | 默认 |
|------|:--:|------|------|:--:|
| `scan` 端口/服务/漏洞探测 | **核心** | 仅扫描目标 | 无需额外 flag | ✅ 启用 |
| `harden` 加固脚本生成 | **核心** | 无 | 无需额外 flag | ✅ 启用 |
| `harden --closed-loop` 闭环 | **核心** | 无（APPLY）/ 仅扫描目标（复扫） | 无需额外 flag | ✅ 启用 |
| `--rules-url` | **补充** | 用户指定 URL | 显式传 URL | ❌ 禁用 |
| `--bark-key` | **补充** | api.day.app | 显式传 Key | ❌ 禁用 |
| `--cve-update` | **补充** | services.nvd.nist.gov | 显式传 flag | ❌ 禁用 |
| Nuclei 模板同步（未来 v0.0.54） | **补充** | GitHub/projectdiscovery | `--sync-templates` | ❌ 禁用 |
| 资产清单远程导入（未来 v0.0.61+） | **补充** | 用户指定 CMDB | `--asset-source-url` | ❌ 禁用 |

### 2.5 README 修正方向

```diff
- 全程离线运行
+ 核心功能离线运行：无需互联网连接即可完成资产扫描、漏洞检测、
+ 加固生成和闭环验证。提供可选联网增强功能（推送通知、远程规则
+ 导入、CVE 更新），均由用户显式 opt-in 控制，默认关闭。
```

> **注**：README 修改**不在本 ADR 范围内立即执行**。等三份 ADR 全部 Accepted 后，在 v0.0.52 统一更新文档。

### 2.6 与 R1 合规红线的关系

- R1（禁止对外主动攻击）：不受影响。补充网络功能均为**被动数据获取**（GET 请求拉规则/CVE/通知），不向外部目标发起扫描/探测/攻击。
- Bark 通知的隐私边界：通知内容仅为**扫描摘要**（目标地址 + 漏洞数量 + 风险等级），不传输扫描详情、规则命中、端口列表。此约束在 `notifier.py` docstring 中已明确，本次 ADR 将其提升为契约。
- 未来 Nuclei 模板同步的 R1/R5 过滤：即使远程拉取，也必须在本地经白名单过滤器后再加载。此过滤机制是 v0.0.54 的门禁前置条件（见 `PROGRESS.md` 约束 #3）。

## 3. 被否决的备选（Alternatives Considered）

| 方案 | 内容 | 否决理由 |
|------|------|---------|
| **B：纯离线（零出站）** | 删除所有 `requests/urllib` 出站调用，外部数据只走文件导入 | ①过度限制用户自主权；②CVE 手动更新更易出错；③不可验证（用户无法审计进程是否真零出站）；④破坏现有 opt-in 功能（需删 ~200 行代码），受益有限。 |
| **C：静默联网（无 opt-in）** | 启动时自动检查 CVE 更新/规则更新，无用户确认 | ①违反"默认零出站"信任模型；②隐私风险——用户不知道自己的扫描目标信息是否随遥测外传；③与本地工具的定位根本矛盾。 |

## 4. 后果（Consequences）

### 4.1 正面

- ✅ **产品身份清晰**：用户知道"我不传 flag 就零出站"，信任模型简单可理解
- ✅ **不需要删代码**：现有 Bark / rules-url / CVE-update 全部保留，与铁律一致
- ✅ **可扩展**：未来新网络功能按同一 opt-in 模式加入，不产生新的身份模糊
- ✅ **可审计**：用户传了什么 flag = 什么功能可能联网，双向透明
- ✅ **R2 多目标 ADR 获得约束框架**：资产清单的来源（本地文件，远程 CMDB 需 opt-in）与离线定义一致

### 4.2 代价

- ⚠️ **README 需要修正**（从"全程离线"→"核心离线 + 可选联网"）——用户可能注意到措辞变化
- ⚠️ **opt-in 的 UX 成本**：用户需要知道哪些 flag 会触发联网——由 `--help` 文本和文档覆盖
- ⚠️ **"核心功能"vs"补充功能"边界需要维护**：新增功能时需判断归类——由本 ADR §2.4 的分类表作为持续参考

### 4.3 对下游 ADR 和版本的约束

| 下游 | 本决策给出的约束 |
|------|------|
| `adr-v052-r2-multi-target-redesign.md` | 资产清单默认**本地文件管理**。远程 CMDB 可选（`--asset-source-url`），需 opt-in + R4 所有权确认 |
| v0.0.55 CVE 扩充 | `fetch_latest_cves()` 保留手动 `--cve-update`。`--auto-sync-cve` 作为独立 opt-in 新增（不默认开启） |
| v0.0.54 Nuclei 模板 | 模板同步为 opt-in（`--sync-templates`），同步后经本地 R1/R5 白名单过滤器再加载。过滤器必须先于同步功能实现（PROGRESS.md 约束 #3） |

## 5. 合规映射（R1–R6）

| 红线 | 本决策落地方式 |
|:--:|------|
| R1 禁攻击 | 补充网络功能为被动 GET 请求，不对外发起扫描/探测/攻击 |
| R2 禁批量扫公网 | 不受影响（网络功能不涉及扫描目标） |
| R3 禁远控后门 | 不受影响（不新增任何入站监听） |
| R4 仅自查自有 | Bark 通知传输目标地址——需在文档中告知用户；通知内容仅摘要级别 |
| R5 MSF 白名单 | 不受影响 |
| R6 频率限制 | `fetch_latest_cves()` 已内置 NVD API 频率控制（5 req/30s 无 key，更高频率需 API key） |

## 6. 验收标准

1. `grep -r "全程离线" README.md` → 0（措辞已修正为"核心离线 + 可选联网"）
2. `--help` 输出中，所有联网 flag 描述包含"需要联网"或"需要网络连接"提示
3. 默认行为（零联网 flag）下，出站请求数 = 0（除向扫描目标本身的探测外）
4. 每条补充网络功能有独立 flag，互不捆绑
5. 三份 ADR（offline / R2 / WSGI）均在 `# 5. 合规映射` 中引用本 ADR 的约束
