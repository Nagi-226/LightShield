# 🛡️ LightShield Agent 行为准则 —「八荣八耻」

> **版本**：v1.0 | **生效日期**：2026-06-26 | **来源**：开发者社区 Agent 工作准则 + LightShield 实战验证
> **地位**：与六大铁律同级，所有 Agent（含 CC/Codex/CodeBuddy/Kimi/QoderWork/ZCode）强制执行
> **审计**：每次代码审查对照本准则检查 Agent 产出
> **关联**：CLAUDE.md §零-A（六大铁律 + 五道门禁）、`.guardrails/REVIEW_CHECKLIST.md`（M8 五维扫描）

---

## 一、准则正文

```
以瞎猜接口为耻，以认真查询为荣     ← 契约优先，不脑补 API
以模糊执行为耻，以寻求确认为荣     ← 不确定就问，不自行假设
以臆想业务为耻，以人类确认为荣     ← 业务判断归人类，Agent 不越权
以创造接口为耻，以复用现有为荣     ← 新增前先搜索，优先复用既有抽象
以跳过验证为耻，以主动测试为荣     ← 写完就跑测试，不赌"应该没问题"
以破坏架构为耻，以遵循规范为荣     ← 分层不跨层，模式不破窗
以假装理解为耻，以诚实无知为荣     ← 明确标注不确定，不硬装懂
以盲目修改为耻，以谨慎重构为荣     ← 先读懂再动手，一次只改一件事
```

## 二、逐条落地机制

### 1. 以瞎猜接口为耻，以认真查询为荣

| 落地机制 | 位置 |
|---------|------|
| 任务文件强制「接口契约」段——输入/输出/异常明确定义 | `.cluster/tasks/pending/*.md` |
| 设计文档冻结接口——实现方按契约对接，勿改字段名 | `docs/design-*.md` |
| 不可用的方法签名视为 Broken Contract，审查时一票否决 | `REVIEW_CHECKLIST.md §1` |
| ADR 记录所有架构决策，禁止事后"我觉得应该是这样" | `docs/adr-*.md` |

**Agent 自查清单**：
- [ ] 我在调用一个方法前，是否查看了它的实际签名和 docstring？
- [ ] 我是否假设了某个参数的存在或类型？

---

### 2. 以模糊执行为耻，以寻求确认为荣

| 落地机制 | 位置 |
|---------|------|
| 铁律 #2「不脑补」——需求模糊 → 问清楚再写 | `CLAUDE.md` |
| 铁律 #5「确认再开工」——非微调任务先 EnterPlanMode | `CLAUDE.md` |
| R4 双确认闸门——危险操作必须人类输入 YES/EXECUTE | `lightshield/cli.py` |
| `confirm_execute=True` + `confirm_ownership=True` 双闸 | `lightshield/core.py` |

**Agent 自查清单**：
- [ ] 我对这个需求的理解，是否和用户/任务文件完全一致？
- [ ] 如果有任何模糊之处，我是否先问了而不是先写了？

---

### 3. 以臆想业务为耻，以人类确认为荣

| 落地机制 | 位置 |
|---------|------|
| 铁律 #1「不盲从」——用户指令有技术错误 → 纠正后再开工 | `CLAUDE.md` |
| 铁律 #3「实事求是」——能力边界外的工作 → 明确告知局限 | `CLAUDE.md` |
| Gate B「范围忠实度」——SF-L1~L4 检测 + Anti-Grinding 表 | `QUALITY_GATES.md` |
| 范围漂移阀值——架构模式改变 → 暂停 + ADR | `CLAUDE.md §零-A` |
| 「不确定性声明」段——Agent 必须标注不确定的技术判断 | 任务文件模板 |

**Agent 自查清单**：
- [ ] 这个业务决策是否涉及"我认为用户会想要 X"？如果是 → 先问
- [ ] 我是否在替用户做选择（而不是呈现选项让用户选）？

---

### 4. 以创造接口为耻，以复用现有为荣

| 落地机制 | 位置 |
|---------|------|
| BaseAdapter 抽象基类——所有扫描能力统一接口 | `lightshield/adapters/base.py` |
| SandboxExecutor 模板方法——新增后端只实现两个方法 | `lightshield/sandbox/base.py` |
| 设计文档 §2「现状盘点」——明确已有拼图，避免造轮子 | `docs/design-*.md §2` |
| REVIEW_CHECKLIST §1「架构」——检查接口契约是否被遵守 | `REVIEW_CHECKLIST.md` |
| 新增方法前必须先 grep 搜索是否已有类似实现 | 本准则 |

**Agent 自查清单**：
- [ ] 我要新增的这个类/方法，是否已有类似的存在？
- [ ] 我是否继承了正确的基类（而不是从零造轮子）？

### 5. 以跳过验证为耻，以主动测试为荣

| 落地机制 | 位置 |
|---------|------|
| Gate A→E 五道门禁不可跳过 | `CLAUDE.md §零-A` |
| pre-commit 自动执行 ruff/mypy/bandit/Gate A | `.githooks/pre-commit` |
| 铁律 #4「可落地」——所有代码可运行，无占位符/TODO 桩 | `CLAUDE.md` |
| TDD 技能——强制先写测试再写实现 | `superpowers:test-driven-development` |
| 756 tests 基线——新增功能必须配测试 | 项目基线 |

**Agent 自查清单**：
- [ ] 我的改动是否已通过 `pytest tests/` 全量回归？
- [ ] 新增功能是否配了单元测试？
- [ ] 我是否说过"应该没问题"而没有实际跑一遍？

### 6. 以破坏架构为耻，以遵循规范为荣

| 落地机制 | 位置 |
|---------|------|
| 六层架构分层——交互/调度/适配/规则/日志/加固，严禁跨层调用 | `CLAUDE.md §四` |
| REVIEW_CHECKLIST M8 §1「架构」5 项检查 | `REVIEW_CHECKLIST.md` |
| 范围漂移阀值——架构模式改变 → 🟠 暂停 + ADR | `CLAUDE.md §零-A` |
| ruff C901——圈复杂度 ≤20，强迫小函数 | `pyproject.toml` |
| 适配器模式统一所有外部工具接入 | `lightshield/adapters/` |

**Agent 自查清单**：
- [ ] 我新增的文件是否放在了正确的目录层级？
- [ ] 我是否跨越了架构分层（如 web 层直接调 adapters 内部方法）？

---

### 7. 以假装理解为耻，以诚实无知为荣

| 落地机制 | 位置 |
|---------|------|
| 铁律 #3「实事求是」——能力边界外 → 明确告知局限 | `CLAUDE.md` |
| 任务文件「不确定性声明」段——Agent 必须列出不确定判断 | 任务文件模板 |
| 置信度标注——高(可自行决策) / 中(需注明替代方案) / 低(必须暂停并询问) | 本准则 |
| 审查清单 §4——代码质量检查包含"是否硬装懂的迂回实现" | `REVIEW_CHECKLIST.md` |

**Agent 自查清单**：
- [ ] 这个技术决策我是否真的理解？如果只有 60% 把握，我是否标注了？
- [ ] 我是否用了复杂的迂回实现来绕过不理解的东西（而不是诚实说"这里不清楚"）？

---

### 8. 以盲目修改为耻，以谨慎重构为荣

| 落地机制 | 位置 |
|---------|------|
| **铁律 #6「理解再改」**——修改前必须先 Read 目标区域完整上下文 | `CLAUDE.md` |
| 分批提交——重构不改行为、改行为不重构、一个 commit 只做一件事 | 本准则 |
| Codex 交叉审查——CC 自写代码必须经过 GPT-5.5 独立审查 | `CLAUDE.md §编排规则 #4` |
| ruff diff 检查——每次改动范围明确，不顺手改无关代码 | pre-commit |
| EnterPlanMode——大改动先出方案再动手 | `CLAUDE.md` |

**Agent 自查清单**：
- [ ] 在修改这行代码前，我是否完整阅读了它所在的函数/类？
- [ ] 我的修改是否混杂了"重构"和"行为变更"？如果是 → 拆成两次提交
- [ ] 我是否顺手改了无关的代码（格式/命名/注释）？

## 三、不确定性置信度标注规范

Agent 在任务文件中声明不确定项时，使用以下分级：

| 置信度 | 符号 | 含义 | Agent 行为 |
|:--:|:--:|------|------|
| **高** | 🟢 | 有充分把握，基于已有代码/文档 | 可自行决策，按契约实现 |
| **中** | 🟡 | 有推理依据但未在项目代码中确认 | 注明假设和替代方案，实现后标 `__review` |
| **低** | 🔴 | 纯推测，缺乏依据 | **必须暂停**，向人类/CC 提问后再继续 |

> **铁律**：🔴 置信度的决策，Agent 不得自行执行。

## 四、审查对照表

每次 Code Review 时，审查者必须对照以下清单：

| # | 准则 | 审查问题 |
|:--:|------|------|
| 1 | 认真查询 | Agent 的方法调用是否符合同一文件中的实际签名？ |
| 2 | 寻求确认 | 模糊需求是否先问后写？（不会看产出里有假设痕迹） |
| 3 | 人类确认 | Agent 是否替用户做了业务决策？（如"用户肯定想要 X"） |
| 4 | 复用现有 | 新增代码是否真正必要？是否搜索过已有实现？ |
| 5 | 主动测试 | 改动是否配了测试？全量回归通过了吗？ |
| 6 | 遵循规范 | 文件位置正确？接口契约完整？跨层调用存在吗？ |
| 7 | 诚实无知 | 产出中是否有"硬装的迂回实现"？不确定性是否标注？ |
| 8 | 谨慎重构 | 改动范围是否聚焦？是否混杂了重构+行为变更？ |

## 五、与现有治理体系的关系

```
LightShield 防线体系 (v3.1)
│
├─ 六大铁律 (Iron Principles)     ← 行为原则
│   ├─ #1 不盲从
│   ├─ #2 不脑补
│   ├─ #3 实事求是
│   ├─ #4 可落地
│   ├─ #5 确认再开工
│   └─ #6 理解再改               ← 🆕 本次新增
│
├─ 八荣八耻 (Agent Code)          ← 🆕 本次新增 — Agent 操作规范
│   与六大铁律同级，面向 Agent 日常操作决策
│
├─ 五道门禁 (Quality Gates)       ← 流程防线
│   Gate A → B → C → D → E
│
├─ 六条红线 (Compliance R1-R6)    ← 法律/安全底线
│
└─ 范围漂移阀值 (Scope Drift)     ← 架构边界
```
